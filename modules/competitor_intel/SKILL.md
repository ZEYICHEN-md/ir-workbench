# competitor-intel · 竞对情报库

按公司与主题累积 peers 动态。设计与理由见 [ADR 0002](../../docs/adr/0002-competitor-intel-store.md)，
这里只写怎么操作。

## 它解决什么

每周写新闻精选时已经在搜 Global OTA 动态，但成果只存在于当期文档里。到季度做竞对研究时
要重新回溯采集。库把周报的副产品留下来，让两件事变成查询而不是重新采集：

| 场景 | 切法 | 命令 |
|---|---|---|
| 写 Appendix：这家公司这季度干了什么 | 按公司纵切 | `ir intel company EXPE --since 2026-07-01` |
| 季报定位：peers 在某主题上都做了什么、怎么说 | 按主题横切 | `ir intel topic distribution` |

## 三条采集通道

| 通道 | 节奏 | 覆盖 | 入口 |
|---|---|---|---|
| 周度 | 每周，随新闻精选 | 全部名单（含 TCOM） | `ir intel deposit` |
| 季度 | **按需**（原定跟财报季，2026-08-25 降级） | 建档层的**表述类**（电话会 / 财报口径） | `ir intel add --file <json>` |
| 专家访谈 | 按访谈到达 | 所有访谈中的增量事实、公司信息、内部经营数据；独立数字不要求绑定论点，以 claim 记录口径、数据期与可信度 | `ir expert-calls intel-draft` → 人工核对 → `ir intel add --file ...` 预演新增/佐证/冲突/疑似口径不同 → 明确确认后 `--commit` |

季度通道**是真的额外工作**，不要假装它是副产品——这也是它被降为按需的原因：
日常主要看动作类，真要做季报定位、需要 peers 原话时再专门跑一轮。

### 季度材料：完整抽取 → 正常项自动入库 → 异常审核

季度材料使用专用入口 `ir intel quarterly`，不把任意 JSON 直接交给通用入口：

1. 只读扫描 `peers_rs_update/companies/<TICKER>/<YYQn>/`，为每个文件记录 SHA-256，并按载体分级：监管文件与公司 IR 原件为 **P0**；管理层电话会内容若只有 AlphaSense/Broker transcript 载体，记 **P1**；摘要、笔记等派生产物为 **P2**。
2. Agent完整抽取有独立检索价值的经营数据、已发生事实、组织动作、经营机制和管理层口径；数字拆成原子 claim。标准财务报表不逐行复制，但影响经营判断的KPI、驱动因素和指引变化要保留。
3. 每条记录必须写 `source_type`、`source_authority`、工作区相对 `source_path`、PDF页码、管理层原话及已核主题。来源不在manifest、分级不一致、只指向TXT派生文本、没有PDF页码，任何一项都会硬停。
4. **校验通过且无异常的P0/P1条目直接进入正式库，不逐条等人批准。**电话会管理层表述可以自动入库，但第三方逐字稿仍标P1，不能写成监管确认事实。
5. 只有数值冲突、口径不清、低置信度、转录含`[indiscernible]`或Agent显式加了`review_flags`的条目进入异常审核队列；系统不自动选数。人工确认异常项时，仍只读取同一份canonical draft。
6. 审核后若材料包任一文件SHA-256变化，异常项提交硬停并要求重跑。正式存储仍调用同一个`Store.add()`，不建立第二套库。

`--dry-run`只用于流程测试；日常正式运行默认自动沉淀正常项。原件继续留在旧材料目录，旧`peers_rs_update`流程不运行、不搬文件。

## 周度沉淀：草稿 → 确认 → 入库

```powershell
ir intel deposit --dir <放精选的目录>      # 出草稿，无副作用
# 人核对草稿（可直接改里面的 topics / companies）
ir intel deposit --commit --period 2026-08-W2
```

三条要点，每条都踩过：

1. **`--commit` 读草稿，不重新解析原文。**重新解析会把人改过的标签冲掉而人不会发现。
   「确认的就是看过的那一份」这条性质比省一次解析重要。
2. **草稿里放的是归一后的条目。**早先放解析结果原样，于是一条提到携程的条目在草稿里
   显示 `shareable`，入库时才被规则改成 `internal`——那等于给了核对的人一份假清单。
3. **精选文件名是中文，用 `--dir` 让命令自己 glob，别把中文路径当参数传**（ADR 0007）。

## 改标签

ADR 0002 说打标「自动，事后可改」。两条改法：

```powershell
ir intel retag                          # 按当前关键词规则重算，先摆差异
ir intel retag --commit                 # 确认后写入并重建档案
ir intel set-topics --id "标题片段" --topics b2b org --commit   # 人工改一条
```

`set-topics` 会把该条标为**已核**，`retag` 此后不再动它。没有这道保护，「事后可改」
是空话——人改完，下一次按关键词重算就把它算回去了，还不会有任何提示。

`retag` 只重算周度通道的条目：季度与访谈通道的标签是人手打的，不该被关键词覆盖。

## 打标：谁定、定什么

| 字段 | 谁定 | 说明 |
|---|---|---|
| 公司 | 规则匹配 | **标题里出现＝主角，只在正文出现＝提及**。精选标题本来就写「谁做了什么」，实测 10/10 正确 |
| 日期 | 规则 | 取来源表的媒体日期，不是发布日 |
| 正文 | 原样搬 | 一个字不改（ADR 0002 §1） |
| **受控主题** | **Agent 读完条目定** | 关键词只给起点，**你要在草稿里定稿**，再请人过一眼 |
| **自由标签** | **Agent 定** | 不限词表，捕捉受控主题装不下的具体性 |

**关键词不是判定器，是起点。**它的定位曾经写错过——文档写「主题是关键词猜的，请你核对」，
等于把语义判断推给使用者。正确的分工是：关键词给个候选，**你（Agent）读完条目定稿**，
人只需要扫一眼有没有明显不对。实测四期 39 条里 28 个关键词标签只靠正文一个词命中、约一半是错的，
指望使用者一条条纠是不现实的。

草稿里的 `topic_hits` 写明每条命中了哪个词，正是给你判断「这个候选靠不靠谱」用的。
主题猜不出的条目会被拒收并列进待处理清单——不会被悄悄丢掉，你补上就行。

改过的条目记得标 `topics_reviewed`，否则下一次 `retag` 会按关键词把它算回去。

### 为什么主题固定 10 个，标签却不限

这是两层，用途不同：

| | 受控主题 | 自由标签 |
|---|---|---|
| 数量 | 固定 10 个 | 不限 |
| 用途 | **跨公司横切比较** | **找回某件具体的事** |
| 例 | `distribution` | `AEO`、`交换费`、`减值`、`agentic预订`、`GEO` |
| 承诺 | 完整（每条至少一个主题） | 不承诺完整 |

固定 10 个主题确实装不下事件本身的具体性——这是真的短板，所以有了自由标签那一层。
但**主题不能也放开**：同一件事在 Booking 下记「分发」、在 Expedia 下记「流量入口」，
「peers 在这个主题上都做了什么」就查不全，而那正是这套词表存在的唯一理由（ADR 0002 场景 2）。

查标签：`ir intel tag`（不给标签名则列全部词频，同义词飘了能一眼看出来）。

## 专家数据 claim 与冲突审查

专家报出的数字不是库里的“真值”，而是带来源的主张。具备独立检索价值的数据不必先绑定论点；每条原子 claim 至少记录：稳定 `metric_key`、结构化 `scope`、数据期 `claim.period`（区别于采集期 `Entry.period`）、`value`、`unit`、比较口径 `basis`、证据类型、来源距离、置信度和理由。原话、页码、专家身份及局限仍放在条目本身。

`ir intel add` 每次都相对当前正式库、跨批次待核池和本批候选动态重算：同指标同数据期但无历史项为「新增」；scope/unit/basis 一致且值相同为「佐证」；口径一致但值不同为「冲突」；scope、unit 或 basis 不同/缺失为「疑似口径不同」。每个匹配项会标明来自 `formal`、`deferred` 还是 `batch`。分类只用于预演审查，不固化为永恒状态。系统只追加主张，不覆盖旧值，不自动合并区间，也不替人选一个“正确答案”。旧的56条普通情报无需回填 claim；以后出现可比公开或专家数据时再按需补。

### B 类待核池与人工转正

A/B 是情报可用性分组，不是飞书候选档位。A 类已有足够来源和口径，可以经确认进入正式库；B 类有检索价值，但缺少分母、时点、范围、第二来源或直接证据，暂时不能脱离访谈上下文使用。

人工选定的 B 类先用 `ir intel defer --file <审核文件>` 预演，明确确认后才带 `--commit` 写入 `data/intel/deferred.jsonl`。待核记录保存来源 run、暂缓原因、转正条件和优先级；它们参与后续 claim 冲突/佐证召回，但 `company`、`topic`、`tag` 和公司档案仍只读正式 `entries.jsonl`。

转正只走 `ir intel promote --id <条目id或唯一标题片段>`。默认仍是 dry-run，展示暂缓原因、补证条件及与正式库/待核池的比较；人工明确确认后才带 `--commit`。写入顺序是先追加正式库，再原子移出待核池并重建档案；若中途在两步之间中断，重试会发现正式库已有同 ID，只清理待核副本，不重复追加。系统不自动转正。

## 硬纪律

- **采集不设限，发布设限（TCOM）。**TCOM 与其他建档公司同等待遇照常收；但
  **新闻精选不得出现任何 TCOM 的动作与表述**。库反向给精选供料时走
  `query.for_digest_supply()`，它一律排除 TCOM。
- **沾到 TCOM 的条目自动标内部级**，不进公开作品集仓。这条在 `normalize()` 里强制，
  不靠人记得。
- **公司档案是投影，不是第二份真源。**`data/intel/profiles/*.md` 由 JSONL 生成，
  手改会被 `ir intel rebuild` 覆盖。要改内容就改 JSONL 那条。
- **入库门槛低**：已发生的事实 + 有可核对来源 + 有明确日期。专家访谈中的数据或事实只要本身有检索价值，且时间、口径、原话与位置可核对，就可以留存；不要求先支撑某个论点。支持、反驳或暂时无法形成结论的数据同样记录，并在 `note` 标明用途和不确定性。排除无新事实的观点稿、纯促销、纯预测，以及口径无法辨认的孤立数字。噪音靠三层名单控制，不靠提高门槛。

## 存储

```
data/intel/
  entries.jsonl        # 正式真源；公司/主题/档案查询只读它
  deferred.jsonl       # B 类跨批次待核池；参与 claim 比较但不进入正式查询
  companies.json       # 其他桶注册表（自动登记）
  profiles/<KEY>.md    # 建档层 8 份人读投影
```

`ir intel status` 报体检：条目数、期次、建档层覆盖、未用到的主题。
`ir doctor` 会额外查真源能否解析、投影有没有落后于真源。

## 已知缺口

- **建档层周度通道里 MEITUAN 仍可能偏少。**迁移回填时 MEITUAN / TCEL / FLIGGY 都为 0；
  2026-08-W4 后 TCEL 与 FLIGGY 已有周度条目。2026-09-02 已把美团 26Q2 财报与电话会按季度通道入库，档案不再是 0。
  周度新闻仍可能偏少，名单不动；`ir doctor` 只在某家连续为 0 时提示。若连续多期有明显公开动作却仍无周度条目，才判定为采集漏项。
- **表述类条目从专家访谈通道按需增加。**人类提供访谈后，`expert-calls` 会先于飞书选择生成带原话与位置指针的内部草稿；即使访谈未进入飞书精选，其中有增量且可核对的事实仍可经人工确认后写入。正式入口沿用 `ir intel add --file ...` 预演与 `--commit` 门禁，不建立第二套存储逻辑。
  schema 中「必须带原话 + 位置指针」的硬校验保留，不能把摘要转述伪装成原话。
