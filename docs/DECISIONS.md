# 设计决策日志

整合三个旧项目为统一工作台过程中的全部设计选择。一次 grilling 式访谈的产物（2026-08-22）。

体例：**问题 → 结论 → 理由 → 落在哪**。重大且难逆的决策另有 ADR；此处是全景索引与轻量决策的唯一记录。

---

## 一、分发与移交

### Q1 交接那天，同事到手的是什么

**结论**：zip 做首次安装；GitHub 私有仓做持续更新（同事不碰 git，Agent 代跑拉取）。公开作品集仓与内部工作仓分离，数据材料只进内部仓。

**理由**：zip 是快照，有三个死穴——没人能重新打包（接手人不写代码）、没有更新通道（几个月后两人版本不同而无人知晓）、活的 Excel 进不了快照。所以 zip 只解决第一次装。

**落在**：ADR 0003 §1、`docs/GLOSSARY.md`（首次安装包 / 持续更新通道 / 公开作品集仓）

### Q4 接手人的技术水平

**结论**：非技术背景。不写代码、不进终端、不用 git、不读 traceback，只用自然语言。业务判断能力强，缺的是操作能力。

**理由**：这条是全部设计的约束源头——它决定了 CLI 不能是人的入口、语义不能绕弯、门禁必须由系统而非人的记忆保证。

**落在**：`docs/GLOSSARY.md`（业务接手人）

### Q22 仓的拓扑

**结论**：单一内部私有仓装全部域 + 共享数据层 + 情报库；三个旧仓冻结不动；另开公开作品集仓（由导出脚本生成，非 git 镜像）。

**理由**：一份共享 Excel、一个横跨周与季的情报库、一套 doctor/config、一次 zip 交付——四条都要求单仓。公开仓用导出而非镜像，因为过滤含敏感材料的 git 历史比重新导出风险高。

**落在**：ADR 0003

### Q-飞书 飞书工作流绑谁的账号

**结论**：绑本机当前 `lark-cli` 登录的同事，不绑工作台作者。仓库只沉淀部门共享资源（Wiki URL、文档 token、群名）和通用步骤；禁止写入个人 `open_id` / CLI 应用 ID。

**理由**：工作台要分发给任意同事。飞书 CLI 的授权模型本来就是「每个人在自己电脑上用自己的飞书登录」。卡片发给自己再转发，是因为每个人的 CLI 应用可见范围通常是仅本人——这条换人仍然成立。Wiki 能写，是因为这位同事对部门文档有权限。

**落在**：`conventions/lark-cli-windows.md`、`docs/GLOSSARY.md`（飞书操作者）、`AGENTS.md` 绝对不做

## 二、入口与客户端

### Q2 一个入口 = 自然语言路由，还是 CLI

**结论**：**两层都要。**顶层路由 skill 是人的入口；CLI 是 Agent 的手，同事永远看不到。

**理由**：这个问题我原本问成了二选一，是错的。Travel_Pulse 的 `CONTEXT.md` 早已定死「Control Plane 被 Agent 和 Operator 使用，不是 Analyst 的直接接口」。真实差别不是「自然语言 vs 命令行」，而是 **Agent 背后有没有状态和门禁**——没有内核，换个会话就不知道停在哪，部分失败也会产出看似完整的东西。

**落在**：ADR 0003 §4、`router/ROUTER.md`、`workbench/`

### Q3 哪个 agent 客户端是正式的

**结论**：Cursor 为基线（公司有会员），同时保证 Claude Code 可用。规则只有一份真源，`.cursor/` / `.kiro/` / `.claude/` 只放指路薄壳。

**理由**：同事只把 AI 当 chatbot 用、只输入自然语言——这正是我们要的用法，说明顶层路由的措辞比客户端更重要。薄壳而非复制，是为了避免 Travel_Pulse 里 `.agents/skills` 与 `.claude/skills` 那种 28 目录镜像双份。

**落在**：ADR 0003 §5

## 三、数据权威

### Q5 Excel 要不要成为共享数据层

**结论**：要。全工作台只有一份指标底稿。

**理由**：两个域读同一张表、各存一份、各写一套 parser，且「当前版本」语义相反（一边按文件名取最新，一边禁止猜选）。更硬的证据：航空 pipeline 当时正在写 `0703_Travel_Pulse` 里停在 0803 的旧表，而实际维护的是 `database_matain` 的 0817——**这条自动化实质上是断的。**

### Q5-a Excel 是权威（读法二），还是 canonical JSON 是权威（读法一）

**结论**：读法二——Excel 是唯一真源，指标快照可全量重建、不接受手改；配一道 diff 门禁。

**理由**：读法一有撤回死锁（清空 Excel 格不生效，想撤回只能手改 JSON，而规则禁止手改）、静默分叉、parser 挂了不可见。但决定性的理由是**可移交**：读法二只有一句话「那张 Excel 就是我们的数据，改它就行」，读法一要求理解一个绕弯，文档写得再清楚半年后也会失传。代价核实后很小（快照只装一年、洞察已独立成文件、parser 覆盖面一一对应）。

**落在**：**ADR 0001**（取代 `database_matain/docs/adr/0002`）

### 指标底稿用哪一份

**结论**：`国内行业数据_0817.xlsx`。已复制到 `data/workbooks/` 并用 `ir config set industry` 锁定。

**理由**：与 `travel.json` 的 `meta.sourceExcel` 一致。按 ADR 0001，系统不按文件名猜最新，须人指定。

### Q7 航空月度自动写入还要不要

**结论**：保留。

**理由**：省人工，且它反而是「Excel 当底稿」的加强论据——Excel 成为人工输入与自动化输入的唯一汇合点，方向单一、好验证。它的成功判据也因此明确为「Excel 四个目标格正确」。

## 四、产物范围

### Q6 / Q10 五部分周报还做不做

**结论**：**彻底停用。**对外交付物收敛成新闻精选一个。最后一期五部分周报是 `2026年7月第3周`。

**理由**：对外需求已经演化成只发新闻精选；行业数据被看板与洞察覆盖，港股改走内部查询。不明确停用的后果是接手人打开 `report-template.md` 会以为要写五部分——正好是「旧入口没有明确停用」这类问题。

**落在**：`docs/GLOSSARY.md` §已停用、`docs/MIGRATION.md` 第 3 步

### Q9 港股保留哪一块

**结论**：全套保留（行情 + 南向持股 + 港美成交额占比）。定位为内部查询能力，不对外。

**理由**：内部想看时要能查到。成交占比的 FY 口径纪律不变。

### Q12 卖方研报怎么办

**结论**：保留为轻量内部查询能力，与港股同待遇；**不并进竞对情报库**，不建持久档案。

**理由**：研报可进情报库的只有事实性内容，而其主要价值是分析师观点与预测——情报库明确排除这两类。加上研报不可外传会带来合规分级麻烦。而「不是特别重要的需求」不该建持久层：持久层有真实维护成本，低频低重要性的能力做成「随时能查」更合适。

**落在**：**ADR 0004**

### Q27 季度行业展望简报还做不做

**结论**：**一次性，不再做。**`docs/briefs/` 整体归档，`generate_brief_charts.py` 与 `publish_feishu_q3_brief.py` 废弃。

**理由**：只产出过 `2026-q3-outlook` 一份，非例行。同时确认了「对外交付物只有新闻精选一个」这句话仍然成立。

## 五、竞对情报库（新建能力）

### 缘起

需求：每周写新闻精选时已在搜 Global OTA 动态，希望按公司沉淀，季度做竞对研究时省掉回溯采集。

关键观察：现有新闻精选**每一条已经是一份合格的情报 entry**（标题 + 含数字的正文 + 竞对含义 + 媒体/日期/URL）。缺的不是内容，只是标签、存储和检索路径。

### 消费场景（决定 schema）

**结论**：两个——① Appendix 撰写，按公司纵切；② 季报定位研究（找自家亮点、决定对外释放什么），按主题横切。

**理由**：场景 ② 要求主题是**受控词表**而非自由标签，否则同一件事在不同公司条目下措辞不同，横切失效。

### Q13 / Q18 覆盖名单

**结论**：三层，分层依据是「要不要建独立档案」而非重要程度。
- 建档层：ABNB / BKNG / EXPE / TCOM / 美团 / 同程 / 飞猪 / 豆包·抖音
- 索引层：MMYT / TRIP（Tripadvisor）/ 途牛 / 华住 / 亚朵 / 万豪 / 希尔顿 / IHG
- 其他桶：其余全部

**理由**：索引层对齐 Q2 Appendix 的实际覆盖（已核对原件：第 322 段「3.其他：MMYT & TripAdvisor & 途牛」，酒店段含五家）。飞猪与豆包·抖音不在 Appendix 内，但作为新出现的分发入口纳入建档层。

**附带钉死的 Ticker 词表**：`TRIP` = Tripadvisor，`TCOM` = Trip.com / 携程，两者绝不用 `Trip` 缩写。起因是 `peers_rs_update/CONTEXT.md` 里「MMYT/TRIP/途牛」极易被误读成 Trip.com。

### Q14 / Q17 什么算「值得记录」

**结论**：入库门槛**低**——已发生的事实 + 有可核对来源 + 有明确日期。排除无新事实的观点稿、纯促销、纯预测。噪音控制在检索侧靠三层名单，不在入库口设严格判据。

**理由**：我原本提了一套五条「改变测试」当门禁，那是把关卡设错了位置。**记录成本低，漏掉后回溯采集的成本才是要解决的问题**——宽进严出才对。

### Q19 收不收「怎么说的」

**结论**：收。entry 分**动作**（做了什么）与**表述**（怎么说的，存原话引用 + 位置）两类。

**理由**：做 IR 定位时 peers 怎么框定一件事常比事实更有用（例：Expedia 电话会把生成式回答那一层叫 **AEO** 而非 GEO）。

### Q15 收不收财报原件

**结论**：不收进情报库。原件放用户指定的当季材料目录，或 `inputs/intel-quarterly/<TICKER>/<YYQn>/`；历史包仍可指向冻结旧仓 `peers_rs_update/companies/<TICKER>/<YYQn>/`。情报库只存引用与位置指针，两边共用同一套 ticker 与季度键。

**理由**：原件体积大、含第三方材料，且 Appendix 写作流水线已退役，不能再把「原件住在 peers-appendix 模块里」当成现行布局。

### Q20 TCOM 建不建档

**结论**：建，且**动作与表述都收，与其他建档公司完全同等待遇**。唯一限制在发布侧：新闻精选不得出现任何 TCOM 的动作与表述；情报库反向为精选供料时须排除 TCOM。

**理由**：写季报要决定对外释放什么，需要知道**携程自己上几次是怎么讲的**——口径前后不一致是实打实的 IR 风险，而这件事此前没有任何地方沉淀。限制放发布侧而非采集侧，是因为采集侧设限会让 TCOM 档案失去唯一的低成本来源，而写精选本来就有人在场，闸放这里执行成本最低。

### Q21 周度沉淀要不要人确认

**结论**：不设确认节点。写完精选自动沉淀，事后可改。

**理由**：正文是人已确认过的，Agent 新增的判断只有公司与主题标签；标签错误可逆、影响只在检索侧。加一道人工会让这个功能的「近零成本」消失。

### Q16 要不要回填历史

**结论**：回填现有 5 期新闻精选与 31 条 ledger 记录，**并把回填当作这个功能的验收测试**。

**理由**：目的不只是补数据，而是在下个季度真要写 Appendix 之前验证 schema 字段够不够用。

**以上全部落在**：**ADR 0002**

### Q26 专家访谈归哪

**结论**：独立成模块 `expert-calls`，首要价值是作为竞对情报库第三条采集通道；飞书 Wiki 只是独立的精选展示分支。所有访谈都可贡献带原话和页码的内部情报，不以是否进入飞书为前提。数据或事实本身有增量、可核对、可按公司或主题找回，就可以留存；不要求先支撑某个论点。条目标内部敏感度，正式入库与飞书发布分别确认。

**理由**：访谈对象多为 peers，能够提供新闻、财报和电话会难以获得的行业数据、公司事实、内部经营数据与机制，天然是情报库的高价值来源。情报库的目的之一就是降低以后回溯取数的成本；若只保存能支持当前判断的内容，会漏掉反例、冲突信号和暂时无法解释但有检索价值的数据，也会形成确认偏差。飞书展示另有锚定数字、篇章完整度和排版要求，一篇访谈不适合做 callout，不代表其中的细粒度数据没有情报价值。

**专家数据口径**：库存的是“某来源在某时间、某范围下提出的数据主张”，不是可被后一个来源覆盖的真值。独立数字拆成原子 claim，记录指标键、范围、数据期、值、单位、比较口径、证据类型、来源距离与置信度。入库预演动态标记新增、佐证、冲突或疑似口径不同；冲突双方均保留，不自动换算、不合并区间、不替人裁决。

**落在**：**ADR 0005**

## 六、Peers Appendix

### Q8 / Q11 谁接手，自动化做到哪一层

**结论**：非技术同事接手。他们**业务上本来就很会做 Appendix**，缺的是操作能力。所以自动化只吃机械劳动（取数、建表、贴图、格式对齐、门禁检查），**绝不吃判断**（写什么、怎么归因）。

**理由**：这与 peers 现有的 gate 设计方向一致，工作量比预估小。附带一个反直觉判断：**低频让它更难移交，不是更容易**——一年只用 4 次，每次都等于重新学，因此对文档和门禁的要求比周报更高。

### Q24 正式入口是哪个

**结论**：`run_earnings_pipeline.py` 为主入口，`update_finance_from_model.py`（Writing）与 `render_ir_snapshot_md.py`（材料阶段）为辅，其余降级为内部实现或废弃。

**理由**：用户不清楚（一直让 Agent 跑），故做了脚本审计。三份文档给了三套不同入口：`docs/pipeline/earnings-summary.md` 与 `MODEL_PERFECT_CONTRACT.md` 只给 pipeline，`scripts/README*.md` 给一堆单步命令，`EARNINGS_SUMMARY_SKILL.md` 给最旧一代 BKNG 链路。

### Q25 脚本两份拷贝，哪份权威

**结论**：**仓内那份权威**（`peers_rs_update/scripts/earnings_summary/`）；`~/.claude/skills/peers-earnings-summary/` 副本删除、不迁。

**理由**：证据判定，不靠回忆。仓内含整代 skill 副本完全没有的内容——`ir_snapshot` 46 处 vs 0 处、`must_cover_in_writing` 3 处 vs 0 处、`audit_model_quarter.py` 704 行 vs 544 行；skill 副本整个缺 `check_writing_gate.py` / `ir_snapshot.py` / `writing_structure_gate.py`，而这三个是 2026-08-09 提交引入的。skill 副本是 08-17 从更旧来源批量安装的快照。用户回忆（在项目文件夹里跑）与证据一致。

**落在**：`docs/MIGRATION.md` § peers-appendix 迁移前置问题

## 七、执行

### Q23 第 1 步（骨架 + Control Plane）能否开工

**结论**：可以，已完成（2026-08-22）。不碰任何现有域。

**落在**：`docs/MIGRATION.md` § 第 0 步

### 周期键要不要统一

**结论**：不统一。周期键按域定义（周报期次 / 数据截至日 / 年月 / 财季 / 查询日 / 无），manifest 索引 = 域 + 周期键。`status` 按域分别报告，不合成全局进度条。

**理由**：一套 period 语义装不下四种节奏；合成一个进度数字会掩盖「某个域三个月没跑过」这类真问题。

**落在**：ADR 0003 §3、`workbench/domains.py`

### 双运行时（Python + Node）留不留

**结论**：改写为 Python，工作台只要一个运行时。9 个 Node 脚本（约 427 行）中 `bootstrap_canonical.js` 废弃，其余改写。

**理由**：接手人非技术，双运行时意味着装两样东西、`doctor` 查两项、zip 安装多一个失败点，与开箱即用冲突；且路径逻辑原本有两套真源。看板文件是纯生成产物，等价性可**逐字节比对**证明，不靠肉眼审。

**落在**：**ADR 0006**

### diff 门禁的摩擦度

**结论**：任何清空都列出等确认；清空 > 10 格、或某序列被清空 > 30%（该序列原有非空 ≥ 5 格）直接 `blocked`。

**理由**：正常每周只新增周次，清空基本不发生，所以「每次都问」几乎零摩擦但真出事一定拦得住。比例规则的最小样本量是实施时被回归测试逼出来的——初版没有它，短序列 1/1 就是 100%，会误伤。

### 周期键用中文还是 ASCII

**结论**：一律 ASCII。`news-digest` 与 `competitor-intel` 的周期键从 `2026年8月第2周` 改为 **`2026-08-W2`**；中文标签由 `Domain.label()` 生成，只用于汇报和交付文件名，**不作键或目录名**。

**理由**：周期键既是命令行参数又是目录名，而 Windows/PowerShell 会**静默损坏**中文参数（`$OutputEncoding` 默认 GBK）。这个 bug 已实际发生过一次——`mark --note` 写进 manifest 的备注变成乱码 `涓婄嚎楠岃瘉…`。若周期键中文，一次事故就会造出 `runs/news-digest/2026骞?鏈?../` 这种目录，难发现、难清理，且下次调用会当成另一期。同时把 CLI 输出强制为 UTF-8（被捕获时原本会因 `✓` 直接抛 `UnicodeEncodeError` 崩掉）。

**落在**：**ADR 0007**（修订 ADR 0003 §3）

### 迁移方式

**结论**：分域搬；每个域「复制 → 改路径 → 真实任务验证 → 删旧」四步一次做完，不留中间态；不在周报或数据更新当周做迁移；旧仓冻结后不得回改。

**理由**：`database_matain` 每周在用，半搬状态下它的脚本会因找不到 canonical 而崩。验证必须用真实任务，不能用 smoke test 代替。

## 八、过程中被修正的判断

复盘时这一节比结论有用——它记录哪些第一版判断是错的，以及被什么推翻。

| 我最初的判断 | 被修正为 | 推翻它的东西 |

| Q2 问成「路由 **还是** CLI」二选一 | 两层都要，分工不同 | Travel_Pulse 的 `CONTEXT.md` 早已定义 Control Plane 不是 Analyst 接口 |

## 九、编排层与后续迁移中的决策（2026-08-22 起）

### 客户端薄壳里要不要重复关键禁令

**结论**：不重复，收成纯指路。`AGENTS.md` 是唯一保证被各客户端自动读到的入口，最危险的禁令写在它里面；`.cursor/rules/`、`.kiro/steering/`、`CLAUDE.md` 只指路。

**理由**：第一版在两个壳里各抄了一遍五条纪律「以防 Agent 不跟指针」。实测 `AGENTS.md` 与 `.kiro/steering/` 都会被自动加载——重复即第二份真源，正是壳里自己写着要避免的事。

### 「下一步是什么」由谁给出

**结论**：由状态机（`steps.py`）统一给出，各命令不硬编码。

**理由**：`merge` 曾同时由自己和状态机各说一遍下一步，输出里出现两条。序列的所有权应当只有一处。

### doctor 要不要懂各域细节

**结论**：不懂。约定 `modules/<域>/health.py` 暴露 `checks(base)`，doctor 只汇总。单个域的检查崩了不影响其余（实现过程中真的救过一次）。

### 底稿结构校验的必要性

**结论**：必须有，且要能抓到列位挪动。`layout.py` 把 16 个指标列的表头与分组名写成显式契约，`ir doctor` 逐项核。

**理由**：`excel.py` 按固定列号取值，**列一挪取到的就是别的指标，而且不会报错**——这类失败技术上合法、业务上全错，最难发现。附带发现国内/国际航空下都有「民航局」「三大航」，只靠指标名分不出，必须连分组名一起核。校验本身有 14 项测试验证它真能抓到 10 类改动——否则它给出的 ✓ 是虚假的安全感，比没有检查更糟。

### 发布门禁

**结论**：`ir industry publish` 默认 dry-run，逐行摆出线上会变什么并把发布仓还原干净；五道硬检查任一不过就拒发（源文件齐全 / 必须 LF / 发布仓无无关改动 / diff 非整份重写 / 无变化不空提交）。

**理由**：其中两道直接来自当天踩的坑。「diff 非整份重写」尤其重要——整份重写通常是格式问题而非内容变化，这种 diff 没法核对，等于放弃验证。把「记得看 diff」从人的纪律变成系统的门禁。

### 酒店 STR 月度用哪个口径（2026-08-24）

**结论**：用**中金周报按天加权聚合**出的月度，不等 STR 官方月报。从 2026 年 7 月起采用；
1–6 月历史值不回改。

**理由**：三个候选摆在一起时差异如下（2026 年 7 月）：

| 来源 | Occ | ADR | RevPAR |
|---|---|---|---|
| STR 官方月报 | -2.3% | -1.0% | -3.2% |
| 券商报告 | -3% | -1% | -4% |
| 中金周报聚合（本方案） | -2.99% | -1.00% | -3.96% |

选它有两条硬理由：

1. **可复现**。原始周报在手上，每月自己能算，不用等别人发图或等券商报告。官方月报慢。
2. **已被独立印证**。券商那组数与本算法几乎逐位吻合（6 月也吻合），说明券商也是这么聚合的。

代价：与 STR 官方月报差 0.7–0.8 个百分点，原因是月报样本集比周报大。对外引用时若有人
拿官方月报核会对不上，这一点要接受。

**过程中被修正的判断**：我一度依据 6 月单月比对下结论「底稿历史一直用官方月报口径」。
把 1–7 月全列出来之后发现不成立——2 月三项几乎等于周聚合（ADR 差 0.02pp），
4 月、5 月却差 2–4pp。**底稿历史值本身就是多来源混合的**，不能作为「该用哪个口径」的依据。
教训：口径判断不能只看一两个月。

**顺带查出的数据质量问题**：7 月 RevPAR 原有 `-5.00%` 是**券商报告里的预计值**，
不是实测。预测值与实测值混在同一列且无标记，系统无法分辨（对 diff 门禁来说都是合法数值）。
已向使用者提出三个处置方案，使用者选择「保持现状，我写了有我的原因」——
风险记录在此：**这条依赖当事人记忆，对接手人不成立。**

**落在**：`modules/industry_data/str_source.py`、`str_plan.py`、
`modules/industry_data/SKILL.md` § 酒店 STR、`tests/test_str_source.py`（22 项）

### 航空管道写入指标底稿：新建带日期文件还是就地更新

**结论**：**就地更新**那份被锁定的底稿（带 staging、独立复算、原子安装、备份）。

**理由**：ADR 0001 定了全工作台只有一份底稿。若管道派生出带日期的新文件，人手填（酒店 STR、周度航空）与自动化写入就会落到不同的表上，且需要额外一条「以后改新文件」的规则——这种规则在移交后必然失传。就地更新只需一句话：那张表就是我们的数据。安全性靠 staging + 备份 + git 追踪兜底。

**仍需你确认**：这条决定会修改权威数据文件，属不可逆动作。写入路径已建好但**尚未执行过任何 commit**。

### 港股三个查询要不要伪装成一条流水线（2026-09-02）

**结论**：不要。行情、南向持股、港美成交占比是三个独立的按需问题；每次只在当天 manifest

**理由**：若查一次南向后显示「1/3，尚未完成」，会制造一个并不存在的待办，反而让 `ir status`

### pandas 在 Python 3.14 / Windows 11 上导入卡死如何处理（2026-09-02）

**结论**：仅在 `win32 + Python 3.14+` 的 hk-market 包初始化时禁用 stdlib `platform` 的 WMI
快路径，让它回退到 `sys.getwindowsversion` 与环境变量；不改系统 WMI，不要求接手人手工修电脑。

**理由**：真实迁移验证中，`pandas.compat._constants → platform.machine()` 卡在
`platform._wmi_query(Win32_OperatingSystem)` 超过 4 分钟；faulthandler 栈已定位到该处。
禁用快路径后同一环境约 6 秒导入成功。pandas 这里只需要平台架构字符串，stdlib 回退值足够；
改系统服务的影响面远大于模块内兼容处理。

**落在**：`modules/hk_market/__init__.py`、`tests/test_hk_market.py`

### 文件怎么进工作台、过期怎么清（2026-09-04）

**结论**：人不用记目录。原件拖进对话、放「下载」或说一声，Agent 拷到 `inputs/<域>/<周期>/`。交付物在 `outputs/`。`scratch/` 超 14 天、根目录 `output/` 与 `_tmp/` 可清；`data/workbooks/archived/` 只增不删。真正删除前 dry-run，用户说「确认删除过期临时文件」后才 `ir hygiene --prune --fix`。迁入残留的 `peers_model_scripts/` 与 `update-shareholder-list/` 本机可留作只读参考，不进 Git、不是运行入口。

**理由**：功能配齐之后，接手人会卡住的是「文件放哪、能不能删」。没有可执行的清理，scratch 和误写的 `output/` 会无限涨；文档若继续写「八个模块 / 自动发飞书 / 中文周期键当目录名」，就会和代码再分叉。

**落在**：`conventions/file-lifecycle.md`、`workbench/lifecycle.py`、`ir hygiene --prune`
