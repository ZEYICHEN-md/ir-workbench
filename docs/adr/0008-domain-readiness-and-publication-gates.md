# ADR 0008：域就绪状态与发布门禁分开表达

- 状态：已采纳
- 日期：2026-09-03
- 影响：Control Plane、新闻精选、专家访谈、卖方研报

## 背景

旧状态页用 `modules/<域>/` 是否存在表示 `migrated`，再把最近一次 run 的步骤完成数当成域状态。
这会混淆四件事：代码目录是否存在、CLI 是否能导入、health 是否能导入、真实业务是否完成验收。
制定本 ADR 时，专家访谈最近一次 run 虽是 6/6，真实飞书分支已发布回读，情报分支也完成 A 类
11 条入库和 B 类 8 条待核；但人工批准稿列出 14 条 B 类，另有 6 条当时没有最终处置记录。
这证明 run 完成数不能替代分支验收。2026-09-03 用户确认后，6 条已通过正式 `intel defer` 流程
补入待核池；34 条草稿现已全量分流，`expert-calls` 随后升级为 `validated`。
卖方研报则相反：它按设计不建 manifest，状态页会长期显示“还没跑过”，但真实研报已经验收。

新闻精选还有一处更直接的冲突。顶层规则要求任何飞书写入都须用户明确确认，模块文档却把
Wiki 发布写成定稿后的自动步骤。两种说法同时存在时，Agent 可能按较近的模块说明越过门禁。

## 决策一：发布授权与产物完成分开

生成、校验或导出完成，只说明产物准备好了，不表示可以写飞书、发消息或对外发布。
每一种发布动作都要有独立、明确、可在状态页回显的人类确认环节。这里确认的是上下文中的
具体动作，不是固定口令本身。

新闻精选完成后，Agent应明确问：

> 是否把本期新闻精选发布到飞书 Wiki？这会更新旅业资讯库和历史周报汇总。

用户紧接着回复“OK”“可以”“确认”等肯定答复即可放行，不要求逐字复述“发布本期新闻精选到
飞书 Wiki”。如果中间已经切换话题、跨会话，或Agent此前没有明确提出这项写操作，单独一句
“继续/OK”不能推定为授权，须重新说明目标并询问。发布完成后仍要回读两份Wiki文档。
专家访谈和行业数据同样遵循这套上下文确认，不把某一句固定话当成唯一合法表达。

### 为什么不沿用一句话全自动发布

一句话跑完本地采编很方便，可以保留。飞书写入会改变共享文档，错误的影响范围和本地生成不同，
而且可以在发布前自然停住，不会增加重复劳动。这里选择多一次明确确认，换取可逆性和责任边界。

### 为什么保留状态页的建议短语，但不做逐字匹配

状态页面对的是跨会话恢复，需要告诉接手人当前待确认的是哪一项，所以仍显示“发布本期新闻精选
到飞书 Wiki”这类完整建议短语。它是消除歧义的提示，不是密码。如果Agent刚刚已经把目标文档、
动作和影响说清楚，用户回复“OK”同样是有效确认。

完全接受任意位置的“好/继续”会误放行；只接受固定句子又会增加无意义的操作负担。本决策选择
上下文确认：先有明确问题，紧接着有肯定答复。

## 决策二：域状态使用四个独立事实

Control Plane 对每个域分别报告：

| 字段 | 含义 | 真源 |
|---|---|---|
| `module_present` | 模块目录存在 | 文件系统 |
| `cli_loaded` | CLI 模块能导入且有 `register()` | 运行时探测 |
| `health_loaded` | health 模块能导入且有 `checks()` | 运行时探测 |
| `validation_state` | 真实业务验收成熟度 | `workbench/domains.py` |

`migrated` 暂时保留为 `module_present` 的兼容别名，但新代码不得用它推断可运行或已验收。
CLI 与 health 的导入错误不再静默跳过：`status` 和 `doctor` 必须显示具体组件及错误。

`validation_state` 有四个值：

- `validated`：既定范围已完成真实业务验收。
- `partial`：仍有已经承诺的业务分支没有闭环；全局状态返回 `partial`。
- `lightweight`：能力范围有意较窄，不建长期状态；不因此报故障。
- `unvalidated`：代码存在，但尚无真实业务验收。

当前 `expert-calls` 已升级为 `validated`：真实批次完成飞书回读，34 条情报全量分流为 A 类 11 条
正式入库、B 类 14 条待核、9 条剔除，三组互斥且逐 ID 对账无缺口；`sellside-research` 为
`lightweight`；其余五域也为 `validated`。最近一次 run 的完成数继续保留，但只描述那一次运行，
不再代表整个域迁移完成。

### 为什么不把 sellside 标成 partial

ADR 0004 已裁定它不建索引、不进情报库、不产生跨期 manifest。这是有意边界，不是欠账。
把它标成 partial 会诱导后来的人补一套不需要的持久层。我们改用合成 PDF 回归和验收记录证明
抽取契约，同时保留真实研报只在本地做业务验收的边界。

### 为什么验收状态仍是声明式字段

真实业务验收包含人工核对、外部系统回读和业务口径确认，无法仅靠代码自动推导。把状态放在
域注册表里，至少比散落在迁移文档和最近一次 manifest 中可控。状态升级必须同时满足：既定分支
真实跑通、门禁与回读完成、迁移文档记录证据。不能因为单元测试通过就把 `partial` 改成 `validated`。

## 被否决的方案

1. **继续用目录存在表示已迁入。**无法发现CLI导入失败，也无法表达部分验收。
2. **把所有域强制成同一种manifest。**会破坏sellside的轻量边界，并让按需查询产生假待办。
3. **只改文档，不改状态输出。**下一位接手人仍会先看到“7个域全部就位”和“6/6”，冲突继续存在。
4. **只问“要不要继续”。**没有把写入对象和影响说清楚，用户的“OK”无法绑定到具体动作；确认问题必须明确指向本期精选和飞书 Wiki。

## 后果

- `ir domains` 与 `ir status` 会返回 `partial`，直到专家访谈情报分支完成真实闭环。
- `ir doctor` 只判断环境和运行时，不因业务验收为 partial 而失败。
- 新增域必须声明验收状态，并同时提供可导入的 `cli.py` 与 `health.py`。
- 新闻精选本地流程仍可一句话完成，但飞书 Wiki 永远是独立发布动作。
- 卖方研报的持续证据使用合成材料，不保存第三方原文、截图或抽取结果。
