# ADR 0002 — 竞对情报库：周报副产品沉淀，供季度研究横切检索

- 状态：**Accepted**（2026-08-22）
- 日期：2026-08-22

## 背景

每周写新闻精选时已经在搜 Global OTA 动态，但成果只存在于当期文档里。到季度做竞对研究时，需要重新回溯采集，成本高且有遗漏。

关键观察：现有新闻精选的每一条**已经是一份合格的情报 entry**——标题 + 3–6 句含具体数字的正文 + 一句竞对含义 + 媒体/日期/URL。缺的不是内容，只是标签、持久化存储和检索路径。

## 两个消费场景（决定 schema）

1. **Appendix 撰写**——按公司纵切：这家公司这季度干了什么，一家一段。
2. **季报定位研究**——按主题横切：所有 peers 在某个主题上分别做了什么、怎么说的，据此决定携程要不要跟进、对外怎么讲。

场景 2 要求主题是**受控词表**而非自由标签，否则跨公司比较失效。

## 决策

### 1. 不重写摘要

沉淀时原样复用新闻精选已写好的正文段落。重写等于额外劳动 + 信息损耗，且会引入「摘要与原文不一致」这类无人可查的错误。

### 2. 覆盖名单分三层

分层依据是「要不要建独立档案」，不是「重不重要」。

| 层 | 名单 | 待遇 |
|---|---|---|
| **建档层** | ABNB / BKNG / EXPE / TCOM / 美团 / 同程 / 飞猪 / 豆包·抖音 | 每期必扫，各自独立档案，季度研究必读 |
| **索引层** | MMYT / TRIP（Tripadvisor）/ 途牛 / 华住 / 亚朵 / 万豪 / 希尔顿 / IHG | 打标签可检索，不单独建档；Appendix 里这些公司主要靠财报材料 |
| **其他桶** | 其余全部（TUI / GetYourGuide / CarTrawler / Agoda / Accor…） | 只存不维护 |

索引层名单对齐 Q2 Appendix 实际覆盖（已核对 `deliverables/2026 Q2 Key Qs_Appendix_0813.docx`：第 322 段「3.其他：MMYT & TripAdvisor & 途牛」，酒店段含华住/亚朵/万豪/希尔顿/IHG）。

飞猪与豆包·抖音不在 Appendix 覆盖内，但作为新出现的分发入口纳入建档层。

**Ticker 词表（写死，防歧义）**：`TRIP` = Tripadvisor；`TCOM` = Trip.com / 携程。禁止用 `Trip` 缩写任一方。

### 3. 入库门槛低，噪音靠分层控制

入库只要求：**已发生的事实 + 有可核对来源 + 有明确日期。**

排除：无新事实的观点评论稿、纯促销活动、纯预测。

不设更严格的「实质性」门槛——记录成本低，漏掉后回溯采集的成本才是要解决的问题。检索侧的噪音由三层名单控制。

### 4. 两类 entry：动作与表述

| 类型 | 内容 | 来源 |
|---|---|---|
| **动作** | 做了什么 | 新闻、公告、公开动作 |
| **表述** | 怎么说的（原话引用 + 位置） | 电话会、财报、公开演讲 |

表述类同样重要甚至更重要：做 IR 定位时「peers 怎么框定这件事」常比事实本身有用（例：Expedia 在电话会上把生成式回答那一层叫 **AEO** 而非 GEO）。

财报与电话会**原件仍只存 `peers_rs_update/companies/<TICKER>/<YYQn>/`**，情报库只存引用与位置指针，共用同一套 ticker 与季度键。

### 5. 主角与提及是放置规则，不是过滤器

两者都记录。主角进公司档案正文；仅被提及的只进检索索引。

例：Airbnb–CarTrawler 租车那条，ABNB 是主角，但「Expedia 年内完成对 CarTrawler 的收购」对 EXPE 是实质信息，须出现在 EXPE 的检索结果中。

### 6. 一条 entry 可挂 0 到 N 家公司

宏观与政策类条目没有公司归属（例：「美国海外入境连续四月下滑」），但对写出境需求侧风险有用。schema 不得强制要求公司字段非空。

### 7. 主题受控词表（初版，可增删）

分发与流量入口（AI 入口 / 内容平台 / 比价 / SEO-AEO）｜供给与品类扩张（体验 / 租车 / 机票 / 短租）｜B2B 与企业差旅｜忠诚度与会员｜费率佣金与业主商户经济｜AI 产品与技术底座｜并购投资与资本配置｜组织与人事｜财务表现与指引｜政策监管与宏观

### 8. 两条采集通道

| 通道 | 节奏 | 覆盖 | 成本 |
|---|---|---|---|
| **周度通道** | 每周，随新闻采集沉淀 | 全部名单（含 TCOM） | 近零 |
| **季度通道** | 跟财报季 | 建档层的表述类条目（电话会 / 财报口径） | 需专门一步 |

### 9. 采集不设限，发布设限（TCOM）

这是本 ADR 里唯一的公司级特例，且**只作用在发布侧**：

- **采集侧不设限**：TCOM 与其他建档公司完全同等待遇，动作与表述都收，周度通道照常覆盖。
- **发布侧硬纪律**：新闻精选**不得出现任何 TCOM 的动作与表述**。这是既有编辑纪律，不因情报库而改变。
- 由此派生一道方向闸：**情报库反向为新闻精选供料时（如「延续上期」类提示），TCOM 条目必须被排除。**当前精选是情报库的上游，尚无泄漏路径；此闸为将来预留。
- TCOM 条目默认标**内部**敏感度，不进公开作品集仓。

把限制放在发布侧而非采集侧的理由：采集侧设限会让 TCOM 档案失去唯一的低成本来源，而发布侧本来就有一道人工确认（写精选是人在写），限制放这里执行成本最低、也最不容易漏。

### 10. 存储形态

沿用已验证的「真源 + 投影」：JSONL 为机器真源（可追加、可去重、可校验）；每家建档层公司一份时间倒序 markdown 档案，作为人读投影。

### 11. 回填并作为验收测试

回填现有 5 期新闻精选（`2026年7月第3周` 起）与 31 条 `news-log.jsonl` 记录。回填的目的不只是补数据，而是**在下个季度真要写 Appendix 之前验证 schema 字段是否够用**。

## 后果

**好的：**
- 周度通道近零成本；季度研究省掉回溯采集。
- 主题横切让「peers 在某件事上都怎么做怎么说」可直接查，直接服务季报定位。
- 两类 entry + 位置指针保证每条都可回原文核对。

**要接受的：**
- 季度通道是真的额外工作，不能假装它是副产品。
- 受控词表需要维护：新主题出现时要显式增补，不能让 Agent 自由造词。
- 建档层 8 家意味着每期扫描面固定，名单变更要走决策而非随手加。
