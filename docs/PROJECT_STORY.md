# IR 工作台：项目复盘与对外介绍

> 状态快照：2026-08-24。本文用于内部复盘、交接、面试和作品集准备。
> 它区分“已实现”“待真实验收”“已设计未实现”，不能把计划中的能力写成已经上线。

## 一句话说明

这是一个面向非技术 IR 同事的 Agent 工作台。使用者只需用自然语言描述任务，Agent 在背后调用统一的编排内核和各业务模块，完成取数、校验、生成、留痕和发布前检查；需要业务判断或会修改权威数据、对外发布的步骤，仍由人确认。

它不是把三个旧项目简单放进同一个文件夹，也不只是一个脚本集合。整合工作的重点是把散落在个人经验、文档和脚本里的工作方法，收敛成一套有统一入口、明确数据权威、运行状态、门禁和恢复路径的系统。

## 先看当前状态

- **平台层**：统一编排内核、Agent 读取的自然语言路由规则、配置、状态记录和基础门禁已经实现。
  另有一层跨域「有什么在等你说话」的汇总，把被门禁停住的动作显式摆出来。
- **业务域**：4/8 个域已迁入。`industry-data` 与 `aviation-monthly` **已完成正式切换验收**；
  `news-digest` 与 `competitor-intel` 已迁入并回填历史，但还没走完一期真实的当周流程。
- **真实运行**：行业数据用真实新一周数据走完 merge → 看板 → 上线，线上核对通过，并实测过回退与恢复；
  航空月度真实写入两份权威 Excel 成功，45/45 校验、回读一致；另沉淀了从中金周报按天加权算酒店月度的能力。
- **对外交付**：唯一对外交付模块 `news-digest` 已迁入，四期历史成品通过结构校验，
  但**下一期真实周报才是它的验收**。
- **交接与分发**：zip、更新通道、操作手册和公开作品集导出尚未完成。

因此，当前版本是“统一内核已落地、两个域完成切换、两个域待首期验收”，不是“完整工作台已上线”。

本文使用以下状态词：

| 状态 | 含义 |
|---|---|
| 已设计 | 边界和方案已确定，代码尚未进入新架构 |
| 已实现 | 新代码和入口已存在 |
| 本地验证通过 | 测试或本地等价性检查通过，未代表真实业务切换 |
| 真实 dry-run 通过 | 用真实输入完成只读演练，没有写权威文件或发布 |
| 正式切换完成 | 真实任务写入、下游同步、发布及人工核对全部通过 |

## 项目背景

最初的三个项目是在两个月的真实 IR 工作中逐步长出来的：

- `0703_Travel_Pulse`：新闻精选、航空月度、港股查询等能力；
- `database_matain`：国内行业数据 Excel、看板、洞察和飞书同步；
- `peers_rs_update`：Global OTA 财报跟踪、业绩总结和 Appendix。

每个项目都解决了真实问题，但长期使用后出现了几类风险：同一份 Excel 有多个副本，规则在不同 Agent 目录重复，正式入口不统一，两个项目对“哪个文件是权威”给出相反答案，有些自动化仍在写已经停用的旧底稿。原作者离开后，非技术同事很难判断该在哪运行、运行到了哪一步、失败后能不能继续。

因此，项目目标从“继续增加自动化脚本”转为“把已有自动化整理成可运行、可验收、可移交、可继续维护的工作台”。

## Before / After

| 整合前 | 目标状态 |
|---|---|
| 三个项目、多个入口，用户要记得去哪个文件夹 | 一个自然语言入口，由路由分派到业务模块 |
| 同一底稿多份副本，路径靠人传入 | 共享数据层只有一份底稿，配置显式锁定 |
| 脚本运行完才知道有没有漏步骤 | manifest 记录每期步骤、输入输出和状态 |
| 失败常以 traceback 或不完整产物出现 | 统一返回 `success / partial / blocked / failed` |
| 对外发布靠人记得检查 diff | 默认 dry-run，发布门禁通过并明确确认后才发布 |
| Cursor、Claude、Kiro 各复制一套规则 | 规则正文只有一份，各客户端只保留指路薄壳 |
| Python 和 Node 混用 | 工作台统一为 Python 单运行时 |
| 交接依赖作者记忆 | 决策、术语、流程、状态和验收标准都落在仓内 |
## 我们实际做了什么

### 1. 先做摸查，没有直接重构

先审计三个旧项目的目录、入口、数据、规则和 git 状态，再通过 27 个设计问题确认使用者、交付物、数据权威、模块边界、迁移顺序和发布纪律。每个重要选择都记录为“问题、结论、理由、落点”，难以逆转的决定另写 ADR。

这一步解决的不是代码问题，而是先分清哪些能力继续保留、哪些彻底停用、哪些只是一次性产物。例如：

- 对外交付物收敛为旅行行业新闻精选；原五部分周报彻底停用；
- 港股全套保留，但改为内部按需查询；
- 月度航空自动写入保留；
- 卖方研报保留为轻量摘读，不建持久库；
- 季度行业展望简报确认为一次性产物，不迁移；
- Peers Appendix 只自动化机械劳动，不替代同事的业务判断。

### 2. 建立统一架构和 Control Plane

已建立顶层自然语言路由和 `workbench/` 编排内核。内核负责：

- 本机配置与工作簿显式锁定；
- 环境自检 `doctor`；
- 分域状态 `status`；
- 按“域 + 周期键”保存 manifest；
- 输入输出 SHA-256 留痕；
- 四态结果语义；
- 客户端统一入口；
- Windows UTF-8、ASCII 周期键和 LF 换行约定；
- 仓库卫生检查和 Windows CI 配置。

人的入口和机器入口被分成两层。业务同事只说“更新国内行业数据”或“做这周新闻精选”；Agent 才会在背后运行 CLI、看 manifest 和处理错误。这里的路由不是另一个机器学习分类器，而是一份由 Agent 读取的意图与门禁规则表。

对外讲解时，可以把几个内部词换成人话：Control Plane 是“统一执行内核”，manifest 是“每期任务记录”，dry-run 是“只演练不写入”，投影是“从权威数据生成、可重建的副本”。

### 3. 迁入 `industry-data`

国内行业数据链已经迁进统一架构，包括 Excel 读表、指标快照重建、看板投影、洞察草稿、飞书计划、发布检查、底稿结构校验和状态机。

最关键的裁决是：国内行业数据 Excel 是唯一指标真源，`travel.json` 只是可重建投影。这样接手人只需记住“改那张 Excel”，不需要理解“Excel 是入口但 JSON 才是权威”的绕弯。

配套完成了清空门禁、列位结构校验和发布 diff 门禁。迁移还暴露并修复了一个旧缺陷：底稿写作 `7月 (preliminary)`，旧解析器只认严格的 `7月`，导致 7 月以后数据长期漏读但没有报错。

当前状态：代码迁移和本地验证已完成；下一次获得新周度数据时（原计划在 2026-08-24 当周进行），要验证新周次追加、`dataUpdate`、洞察过期、飞书新行和 datamax.fun 上线。验收通过前不删除旧实现。

### 4. 迁入 `aviation-monthly`

民航局和三大航月度数据管道已接入统一配置和三步状态机：dry-run、commit、resync。保留了 staging、独立复算、Excel COM 全量重算、原子安装、备份、单元格批注和 provenance manifest。

迁移修复了两个旧缺陷：月份后缀导致 7 月无法定位；三家航司公告格式不同，旧解析器只能识别南航的独立“合计”行，无法识别东航和国航写在指标名行里的总量。

2026 年 7 月真实 dry-run 已经通过 34/34 项校验，但尚未执行正式写入，因为用户还没有明确说“写入”。写入后还要重建行业快照和看板，才能完成真实闭环。

### 5. 为剩余模块完成边界设计和旧实现审计

竞对情报库、专家访谈、卖方研报、港股、新闻精选和 Peers Appendix 的产品边界与迁移顺序已确定。其中竞对情报库已经完成 schema 方向、公司分层、动作/表述条目、主题受控词表和 TCOM 发布规则的设计，但还没有实现 JSONL、检索和历史回填。

Peers 项目已完成 37 个脚本的入口与重复实现审计，并发现 ABNB 写作链走不通、图表步骤写死 EXPE、测试覆盖很薄等问题。由于这些问题还没修，不能对外说 Peers 模块已经迁入。

仓库分为三层：

1. 内部私有工作仓：代码、共享数据、运行记录和内部材料；
2. 独立看板发布仓：只接收看板四个文件，继续部署到 datamax.fun；
3. 未来的公开作品集仓：由导出脚本生成，只含代码框架、合成数据和脱敏示例，不复制内部仓 git 历史。

## 这个项目的特点

### 面向非技术使用者

产品入口不是命令行。命令行是 Agent 的执行层，负责稳定运行和留痕；同事只需要自然语言。这避免了“为了让同事不用命令行，就干脆不做工程内核”的另一种极端。

### 数据权威清楚

每种数据只允许一个真源。国内行业指标以 Excel 为权威，JSON、看板和飞书都是投影；洞察有独立真源；将来的竞对情报库以 JSONL 为真源，公司档案是人读投影。

### 人机边界清楚

系统自动处理取数、校验、建表、贴图、格式和状态记录。数据口径冲突、清空、洞察确认、权威文件写入和对外发布等动作留给人判断。Peers Appendix 也明确不让自动化替代同事的研究判断。

### 默认可恢复，而不是只追求一次跑通

每期任务有 manifest，记录步骤、输入输出哈希和下一步。换一个 Agent 会话也能知道做到哪里。出现部分完成或阻塞时，不会包装成成功。

### 把经验写成可执行门禁

“记得看 diff”“别选错 Excel”“发布前检查换行符”不再只写在文档里，而是变成程序检查。当前两个已迁域的关键清空、底稿结构、公告解析和发布门禁都有回归测试，其他域尚不能这样宣称。

### 迁移以真实任务验收

每个域遵循“复制、改路径、真实任务验证、删旧”。本地 smoke test 只能证明代码能运行，不能证明一周真实新增、飞书写入和线上部署都正常。因此 `industry-data` 刻意等下一轮真实数据再切换。
## 几个能讲清工程价值的真实案例

1. **自动化写错了文件，但没有报错。**航空管道仍指向 Travel Pulse 里停止维护的旧 Excel，真实维护的是另一个项目中的新 Excel。整合后工作簿由统一配置显式锁定，不再靠调用者传路径。
2. **“容错”掩盖了 parser 故障。**旧规则遇到 Excel 空值就保留 JSON 旧值，导致 `7月 (preliminary)` 无法解析时，看板仍显示旧数据，看起来一切正常。改成 Excel 全量重建并加 diff 门禁后，故障立即暴露。
3. **跨运行时改写产生假 diff。**Python 与 Node 对 `0.0`、换行符和键顺序的写法不同。若只比较数据含义，发布时可能看到整份文件重写。项目对行业看板投影做了字节级等价性验证，并统一 LF。
4. **真实来源格式不一致。**三大航公告并非统一模板。新解析器兼容南航的合计行、东航和国航的指标名行，同时保留分项勾稽，避免“为了通用而猜数”。
5. **中文参数在 Windows 下静默乱码。**周期键改用 ASCII，中文只作展示标签；CLI 输出强制 UTF-8。这个选择来自已经发生过的乱码 manifest，不是理论优化。

这些例子比“做了一个 AI 平台”更适合面试，因为能说明你发现了什么风险、如何取舍、如何验证。

## 一个真实任务目前走到了哪里

以“更新 2026 年 7 月航空官方数据”为例：

1. Agent 根据路由识别为 `aviation-monthly`，读取统一配置中的两份工作簿；
2. 抓取民航局和三大航真实公告，解析总量与分项；
3. 独立复算同比、检查分项勾稽、公式错误、底稿结构和既有值冲突；
4. 输出四个目标同比和 34 项校验结果，但不写文件；
5. 这一步已经真实运行并通过；
6. 正式写入 Airline Data 和国内行业数据 Excel 仍在等用户明确说“写入”；
7. 写入后的行业快照重建、看板生成和人工核对也还没有执行。

这个例子能说明自然语言入口、自动校验、人工门禁和跨模块同步是怎么配合的，也能清楚显示当前进度没有被包装成完整闭环。

## 你在这个项目里做了什么

比较准确的角色是：**业务产品负责人、流程设计者和验收责任人**。工程实现采用 AI 辅助方式完成。

### 你做出的决定

- 从两个月的真实工作中识别值得重复使用的任务，并先做出局部自动化；
- 提出统一工作台目标，定义接手人是只会自然语言的非技术同事；
- 决定哪些产物继续做、哪些停用，以及内部能力和对外交付的边界；
- 裁决 Excel 数据权威、业务口径、公司覆盖、TCOM 发布纪律和确认门禁；
- 解释真实工作流程，纠正不符合业务实际的初版设计；
- 要求所有问题、结论和理由持续留档；
- 决定不做假上线，等真实任务完成切换验收。

### AI 辅助完成的工程工作

AI 负责摸查代码与资料、提出备选方案、生成 Control Plane 和模块迁移代码、补测试、定位缺陷和整理文档。对外不应把这些说成全部由你手写。

### 你如何审查和验收

你通过业务口径裁决、真实文件选择、门禁确认、输出核对和是否上线的决定来验收 AI 产出。系统还用回归测试、34 项航空校验、字节级看板比对和真实任务 runbook 提供技术证据。对于尚未真实写入或上线的部分，你明确保留“待验收”状态。

所以，这个项目也不只是“给 AI 发提示词”。你的主要贡献是把业务目标、风险边界和验收标准说清楚，并让 AI 生成的实现接受可重复检查。面试时如果被追问编码参与度，应如实说明采用了 AI 辅助工程，并重点讲你如何发现问题、做选择和判断结果能不能投入使用。

### 2 分钟面试版本

这个项目起点不是从零做平台，而是我在两个月的 IR 工作里，遇到新闻整理、行业数据维护、航空月度更新和 peers 财报跟踪时，分别沉淀了几套自动化。后来我发现这些局部系统开始分叉：同一份 Excel 有多个版本，规则在多个 Agent 目录复制，有一条航空管道甚至还在更新已经停用的旧底稿。

我先没有急着合并代码，而是把使用者、产物和风险边界问清楚。接手人是非技术同事，所以人的入口必须是自然语言；但 Agent 背后仍需要一个统一内核来管理配置、状态、门禁和恢复。数据层上，我们把国内行业 Excel 定为唯一指标真源，JSON、看板和飞书都只是投影。发布、清空和权威文件写入默认停在 dry-run，等人明确确认。

工程上，我把系统拆成八个业务模块和一个共享 Control Plane，统一到 Python 运行时，并为 Windows 编码、换行符、发布 diff、Excel 结构和运行状态加了检查。迁移过程中还修掉了月份后缀漏读、三家航司公告格式不同等旧缺陷。目前编排层已经完成，两个数据模块进入新架构，但仍按真实任务做最后验收；其他模块没有被包装成“已经完成”。

我的角色主要是定义业务边界、数据权威、交付纪律和验收标准，并用 AI 做代码审计、实现和测试。这个项目让我把个人工作方法从零散脚本整理成一套别人能接手的运行系统。

### STAR 版本

**S（背景）**：三套从真实 IR 工作中长出来的自动化分散在不同项目，存在重复规则、数据副本、入口冲突和交接风险，接手人又是非技术同事。

**T（任务）**：在不影响每周和每季正常工作的前提下，把它们整理成一个可分发、可恢复、可持续维护的 Agent 工作台。

**A（行动）**：先审计旧项目并完成 27 个设计问题；确定八个模块、单一内部仓和自然语言/Control Plane 两层入口；裁决 Excel 为指标真源；建立 config、doctor、status、manifest、四态结果和确认门禁；按“复制、改路径、真实验证、删旧”迁移两个数据域，并为解析、结构和发布门禁补回归测试。

**R（结果）**：统一编排层落地，`industry-data` 和 `aviation-monthly` 已进入新架构；真实航空 dry-run 34/34 校验通过；发现并修复多个原先静默存在的问题。项目尚在迁移中，下一阶段是完成真实切换、剩余模块和分发包。

## 对外展示边界

公开作品集可以展示：

- 架构图、路由、Control Plane、状态语义和模块接口；
- 合成 Excel、合成 JSONL、脱敏 manifest 和测试；
- dry-run、门禁、diff 和恢复流程的录屏或截图；
- 经过脱敏的 Before/After 案例。

不能公开：

- 国内行业数据原始 Excel、STR 数据和内部看板明细；
- 券商研报、专家访谈、财报原件和内部飞书配置；
- TCOM 内部条目、访问凭据、真实文档 token；
- 内部仓 git 历史。即使当前文件删掉，历史中仍可能留有材料。

公开仓应由导出脚本从内部仓生成，并用合成数据重新演示。不要直接把内部仓改成 public，也不要把公开仓做成包含内部历史的镜像。
